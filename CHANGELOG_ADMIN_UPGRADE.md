# Admin dashboard and storefront upgrade

## Phase 1 — Product delete and edit

- **Problem/root cause:** The admin catalog had an Edit button but no Delete button and no product-delete server action, so the failure could not produce an HTTP request, response, browser console error, or server stack trace. Consequently, no exact runtime error or stack trace was observed; none is fabricated here. Static inspection also found `ON DELETE RESTRICT` foreign keys from `OrderItem`, `InventoryItem`, and `CartItem` to `Product`, so hard deletion would fail for referenced records. `OrderItem` already stores `productName` and `unitPrice` snapshots.
- **Changes:** Added permission-checked soft deletion (`Product.deletedAt`, `isActive = 0`), confirmation and feedback in every catalog row, and filters to keep archived products out of admin/storefront listings. Checkout already rejects inactive products, so archived products cannot be purchased. The existing editor supports name, description, price, stock, category, and image editing; a successful save now also gives feedback and refreshes the server component. Changed files: `frontend/app/(admin)/actions.ts`, `frontend/features/admin/components/dashboard.tsx`, `frontend/features/admin/server/data.ts`, `frontend/features/storefront/server/data.ts`, `db/database_pb.sql`, `db/migrate.js`, `frontend/features/admin/archive-product.test.ts`.
- **Migration:** Run `npm run db:migrate`; existing databases receive the nullable `Product.deletedAt` column. New databases include it in `database_pb.sql`. No existing products are deleted or rewritten by this migration.
- **Environment:** No new environment variables.
- **Test:** `npm test -- --run frontend/features/admin/archive-product.test.ts` (or `npm test`); verify an admin with `catalog:write` can edit and archive a product, that the confirmation can be canceled, and that archived products are absent from storefront and checkout while old orders still show their saved item name and price.
- **Deployment/manual steps:** Apply the migration before deploying. The original missing-delete UI cannot be replayed against a live browser/database in this environment, so browser network/server-log capture remains unverified.
- **Verification:** Archive tests passed (3/3), `npm run typecheck` passed for web/db/ui, and `git diff --check` passed. `npm run lint --workspace=@princess-brothers/web` is blocked by existing `no-unused-vars` errors in SmoothUI components and the admin dashboard; no unrelated lint cleanup was made. Database migration and browser flows were not run because no isolated local database/browser session was available.

- **Deployment/manual steps:** Deploy web code. The demand aggregate uses existing order and order-item data; no scheduled task is required.
- **Verification:** Demand and archive tests passed (5/5), web typecheck passed, and `git diff --check` passed. No database or browser test was run.

## Phase 4 — Product categories and tags

- **Problem/root cause:** Product metadata had a category relationship but no supported inline category creation, tag model, or tag-aware storefront/admin search. Product descriptions were stored in a 191-character column even though the editor accepts up to 5,000 characters, so longer valid edits could fail in MySQL.
- **Changes:** Added optional unique category slugs, case/trim-insensitive duplicate checks and inline category creation; added `Tag` and `ProductTag` many-to-many tables; added create/edit persistence for up to 20 tags per product, autocomplete from existing tags, and tag-aware catalog search. Storefront search now includes tags and keeps the existing category filter. Product descriptions use `TEXT` to match editor validation. Changed files: `db/database_pb.sql`, `db/migrate.js`, `frontend/app/(admin)/actions.ts`, `frontend/app/(admin)/admin/dashboard/page.tsx`, `frontend/app/admin-tables.css`, `frontend/features/admin/archive-product.test.ts`, `frontend/features/admin/components/dashboard.tsx`, `frontend/features/admin/server/data.ts`, `frontend/features/admin/server/product-metadata.ts`, `frontend/features/admin/server/product-metadata.test.ts`, `frontend/features/storefront/components/product-listing.tsx`, `frontend/features/storefront/server/data.ts`.
- **Migration:** Run `npm run db:migrate`. On existing databases, it widens `Product.description` to `TEXT`, adds `Category.slug`, consolidates existing categories whose names differ only by case/leading/trailing whitespace while retaining product and parent links, adds unique category name/slug indexes, and creates `Tag`/`ProductTag` with foreign keys. Review duplicate category records before applying this migration to production; no migration was run in this environment.
- **Environment:** No new environment variables.
- **Test:** `npm test -- --run frontend/features/admin/server/product-metadata.test.ts frontend/features/admin/archive-product.test.ts frontend/features/storefront/server/demand.test.ts`; verify creating a category with a duplicate name/slug is rejected, tag assignment persists on create/edit, and storefront/admin searches match category and tags.
- **Deployment/manual steps:** Apply the migration before deploying. Existing category duplicates are consolidated to the lowest category ID; review existing category data and take the normal database backup before production migration.
- **Verification:** Web TypeScript typecheck passed; focused metadata/archive/demand tests passed (9/9); migration JavaScript syntax check and `git diff --check` passed. No database migration or browser/API flow was run because no isolated database/browser session was available.

## Phase 5 — Persistent product image storage

- **Problem/root cause:** The admin product upload wrote files under the Next.js app's `public/uploads/products` directory, while the deployment environment can replace application release files. Database image paths were relative to that release, so uploads could be lost or served as 404s after deployment. No deployed image request was available to capture a production status/body.
- **Changes:** Product uploads now use an S3-compatible object store (AWS S3 by default; custom endpoint supports R2 and compatible providers), and new database values are full HTTPS public URLs. Upload errors are logged and surfaced as explicit 503/502 responses. Admin product image validation only accepts legacy UUID paths or a UUID product object URL on the configured public host. Added a dry-run-first migration script to transfer existing local images and update matching product rows, plus a shared image component that falls back to `/products/fruits.jpg` when the selected image returns an error. Changed files: `DEPLOYMENT.md`, `CHANGELOG_ADMIN_UPGRADE.md`, `package.json`, `package-lock.json`, `frontend/package.json`, `frontend/app/(admin)/actions.ts`, `frontend/app/api/admin/products/image/route.ts`, `frontend/app/storefront.css`, `frontend/features/admin/components/dashboard.tsx`, `frontend/features/admin/server/product-image-storage.ts`, `frontend/features/admin/server/product-image-storage.test.ts`, `frontend/features/storefront/components/product-image.tsx`, `frontend/features/storefront/components/storefront.tsx`, `frontend/features/storefront/components/cart-flow.tsx`, `frontend/app/(storefront)/products/[id]/page.tsx`, `scripts/migrate-product-images.js`.
- **Migration:** No schema migration. Before retiring a release containing local uploads, make those files available to the migration host, run `npm run images:migrate` to list candidates/missing files, then `npm run images:migrate -- --apply` to upload and update product URLs. The script only considers UUID filenames under `/uploads/products/`; it skips missing/unsupported local paths and leaves those database values unchanged.
- **Environment:** Set `PRODUCT_IMAGE_S3_BUCKET`, `PRODUCT_IMAGE_S3_REGION`, `PRODUCT_IMAGE_S3_ACCESS_KEY_ID`, `PRODUCT_IMAGE_S3_SECRET_ACCESS_KEY`, and `PRODUCT_IMAGE_PUBLIC_BASE_URL`. Set `PRODUCT_IMAGE_S3_ENDPOINT` for non-AWS S3-compatible storage. Optionally set `PRODUCT_IMAGE_UPLOAD_SOURCE_DIR` when old uploads are not at `frontend/public/uploads/products`. The storage access key must be restricted to the product image bucket; configure public/CDN read access only for `products/`.
- **Test:** `npm test -- --run frontend/features/admin/server/product-image-storage.test.ts`; configure the bucket/CDN, upload an image in the admin editor, and check its public HTTPS URL in a production build/browser. No database or object-store credentials were present here, so upload and URL migration were not executed.
- **Deployment/manual steps:** Configure the S3-compatible bucket and HTTPS public base URL before enabling uploads. Preserve the old upload directory until the migration script reports no missing source images. Product display uses the browser image element with Next's `unoptimized` mode, so no remote image-domain allowlist is required.
- **Verification:** Product-image validation and regression tests passed (11/11 across image metadata/archive/demand suites), web TypeScript typecheck passed, migration scripts passed Node syntax checks, and `git diff --check` passed. Focused lint initially reported an `<img>` optimization warning; the component now uses `next/image` in `unoptimized` mode. Production build and live storage/browser verification remain for Phase 10 and require deployment storage configuration.

## Phase 6 — Driver monthly delivery count

- **Problem/root cause:** The `Driver` model had no current-month delivery counter or retained month marker, and neither the driver portal nor admin assignment view showed completed delivery counts.
- **Changes:** Added `driveCount` and `driveCountMonth` to `Driver`, plus `driver_monthly_stats` keyed by driver and month. Driver delivery completion now increments the count and historical row in the same transaction, only on the first transition to `DELIVERED`; retries do not double count. Reads lazily reset stale driver counters using the MySQL calendar month and initialize them from the current historical row. The migration backfills historical counts when a `ProofOfDelivery` row provides an exact timestamp. Counts now appear in the driver's own profile and admin driver options. Changed files: `db/database_pb.sql`, `db/migrate.js`, `frontend/app/(driver)/actions.ts`, `frontend/features/admin/components/dashboard.tsx`, `frontend/features/admin/server/data.ts`, `frontend/features/driver/components/portal.tsx`, `frontend/features/driver/server/data.ts`, `frontend/features/driver/server/monthly-stats.ts`, `frontend/features/driver/server/monthly-stats.test.ts`.
- **Migration:** Run `npm run db:migrate`. Existing databases receive the two driver columns and monthly statistics table. Existing proof-of-delivery records are backfilled idempotently; completed orders without a proof timestamp are not assigned an invented historical month. The monthly stats FK restricts deletion of a driver with retained history.
- **Environment:** None. Month boundaries use `CURRENT_DATE()` from MySQL; ensure the database server timezone matches the business timezone.
- **Test:** `npm test -- --run frontend/features/driver/server/monthly-stats.test.ts`; complete one assigned delivery and verify exactly one count increase, repeat the same status request and verify no duplicate, then test the first read after a month boundary and inspect the historical row.
- **Deployment/manual steps:** Apply the migration before deploy. Monthly reset is lazy on driver/admin reads; there is no cron service to configure.
- **Verification:** Web typecheck passed; monthly-count and prior catalog regressions passed (13/13); migration syntax and `git diff --check` passed. No MySQL-backed delivery transaction was run because no isolated database was available.

## Phase 7 — Asynchronous order processing

- **Problem/root cause:** The admin order handlers called `window.location.reload()` after advancing order status, approving payment, or assigning a driver, discarding the entire dashboard state and forcing a full navigation.
- **Changes:** Replaced those reloads with optimistic updates to the affected order in local state. Orders move between kanban columns immediately; payment state and driver assignment update in place. Failures and thrown requests roll back the previous row and show actionable toasts. Per-order pending state disables conflicting controls and displays button/loading text. The selected order is derived from the updated collection so its modal reflects the optimistic change. Removed unnecessary admin dashboard revalidation from these actions; customer order pages and the driver portal are still revalidated where needed. Changed files: `frontend/features/admin/components/dashboard.tsx`, `frontend/app/(admin)/actions.ts`.
- **Migration:** None.
- **Environment:** None.
- **Test:** `npm run typecheck --workspace=@princess-brothers/web`; verify successful and failed status/payment/assignment operations in a browser, including rollback and no document navigation.
- **Deployment/manual steps:** Deploy the web app. Browser request/navigation observation was unavailable here.
- **Verification:** Web typecheck passed and focused regressions passed (11/11). Targeted lint on the dashboard still reports pre-existing `no-unused-vars` errors in the file (including unused imports/props elsewhere); no unrelated lint cleanup was made. No browser/API execution was possible without an isolated database and browser session.

## Phase 8 — Driver selection, contact, and chat

- **Problem/root cause:** The order dialog had a driver selector but did not show a selected driver's profile, status/availability, recent deliveries, call details, or chat. Admin driver data did not include photos or recent-delivery details, the Driver model had no profile-photo field, and no database-backed driver/admin message history existed.
- **Changes:** Added a selectable list of all registered drivers with lowest/highest monthly drive-count sorting (count is primary; exact service-area matches break ties). Selecting a driver opens a details panel with profile photo/fallback, phone and `tel:` link, copy-phone action, vehicle, account status/availability, current-month count, and recent orders. Assignment is an explicit action with optimistic in-place updates; inactive or service-area-ineligible drivers remain visible but cannot be assigned. Added a driver profile photo upload using the existing S3-compatible storage, an authenticated five-second polling chat shared by admin and driver portals, message history/timestamps, and responsive panel/chat styles. Changed files: `CHANGELOG_ADMIN_UPGRADE.md`, `DEPLOYMENT.md`, `db/database_pb.sql`, `db/migrate.js`, `frontend/app/(admin)/actions.ts`, `frontend/app/(driver)/actions.ts`, `frontend/app/admin-tables.css`, `frontend/app/api/driver/profile/image/route.ts`, `frontend/features/admin/components/dashboard.tsx`, `frontend/features/admin/driver-selection.ts`, `frontend/features/admin/driver-selection.test.ts`, `frontend/features/admin/server/data.ts`, `frontend/features/admin/server/product-image-storage.ts`, `frontend/features/admin/server/product-image-storage.test.ts`, `frontend/features/driver/components/driver-chat.tsx`, `frontend/features/driver/components/portal.tsx`, `frontend/features/driver/server/data.ts`, `frontend/features/storefront/components/product-image.tsx`, `frontend/public/driver-avatar.svg`.

- **Environment:** No new variables. Driver photos reuse the Phase 5 S3-compatible settings. Ensure the configured HTTPS public URL/CDN serves both the `products/` and `drivers/` prefixes. Messages use the existing MySQL connection; chat polling requires no additional service.
- **Test:** `npm test -- --run frontend/features/admin/driver-selection.test.ts frontend/features/admin/server/product-image-storage.test.ts frontend/features/driver/server/monthly-stats.test.ts`; verify inactive/location-ineligible drivers cannot be assigned, both sort directions, an admin/driver message round trip, and phone/photo display in a browser.
